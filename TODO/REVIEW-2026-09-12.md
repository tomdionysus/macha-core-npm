# Code review — 2026-09-12

A general review of the working tree on top of 0.7.0, including the unreleased changes. Baseline: typecheck, `lint:platform` and all 600 tests pass. Five reviewers worked one subsystem each over the CodeGraph index; the high findings were then verified a second time against the source. Where a reviewer reproduced a finding by running code, that is said.

Items graduate from here to [ACTIVE.md](ACTIVE.md) when they are decided, and to [COMPLETED.md](COMPLETED.md) when they ship. Anything judged not-a-defect should be struck through here with the reason, not deleted.

The overall shape: the design is well argued and the comments record why. The defects sit at the seams between mechanisms that are each correct alone — promotion versus superseded cleanup, failover versus a still-live player, the seek guard order — and several are the class HISTORY already records as paid for once: a replacement path that drops the segment container.

## High

### ~~H1 — Promotion never closes the abandoned primary~~ — FIXED, unreleased
`src/playback/PlaybackCoordinator.ts:1239`, `:1511`. **Confirmed, reproduced.**

`promoteReadyAlternate` passes a fresh object to `beginSupersededCleanup`, whose first line returns unless that object is already `this.supersededCleanup`. It never is, so the call is a no-op and nothing else touches the primary on this path. After degradation, promotion, and the replacement streaming, `resolver.stop` has zero calls. On a one-slot node the old transcode session holds the slot for `session_idle`, 30 minutes. The new comment at `:1132` ("every path here that abandons one calls `resolver.stop()`") is false for this path.

Fix: assign `this.supersededCleanup = cleanup` before the call, mirroring `recoverFromSourceFailure:1581`, or stop immediately. Assert the stop in the promotion tests at `PlaybackCoordinator.test.ts:919-942`, which check only the play call.

Load-bearing beyond the leak: the Android TV client reports (2026-09-12) that its seamless-failover work runs a *second concurrent session* on a one-slot node, so the slot arithmetic only balances if the promoted-from session actually closes. This was a precondition of that feature, not only a tidiness fix.

### H2 — A second failure during an in-flight failover goes terminal
`src/playback/PlaybackCoordinator.ts:1500-1508`. **Confirmed.**

`failNow` starts recovery only when `!this.failoverPromise`; otherwise it falls to `failTerminal`. The old player is neither stopped nor unsubscribed during failover, so it keeps emitting. hls.js fatal → failover POST in flight → the element plays out its buffered tail and emits `ended` short of duration → `premature-source-end` (`:1443`) calls `fail()` again → terminal. The runtime closes the coordinator and the freshly created replacement is thrown away via the disposed path.

Fix: when a failover is in flight and the error is endpoint-retryable, log and drop it (the posture `promoteReadyAlternate` already takes), or `player.stop()` when failover begins. No test sends two failure signals from one dead source.

### H3 — A slow admission that succeeds after the deadline is stranded
`src/playback/ClusterPlaybackResolver.ts:22-42`, `:226-228`.

`awaitWithEndpointDeadline` rejects at 12 s and leaves the POST running, but once `settled` is set the late result is dropped: never put in `sessions`, never returned, never deleted. The idempotency key does not help because sessions are node-local. The slow node — the one the deadline exists to route around — holds a session, and on a one-slot node its only transcode slot, for 30 minutes. Tests use only never-settling promises (`ClusterPlaybackResolver.test.ts:217,246`, `fakeCluster.ts:121`).

Fix: after a deadline rejection, chain `request.then(session => resolver.stop(session.sessionId))` and log it. Test a POST that resolves after the deadline and assert a DELETE follows.

### H4 — The ranking comparator is not a consistent order
`src/cluster/EndpointRegistry.ts:245`, `:281-309`, `:415-437`, `:469-479`. **Reproduced by compiling the registry and driving it with three endpoints.**

Every measured axis compares pairs against a threshold (40 % relative, 50 ms absolute). Threshold indifference is not transitive: A≈B, B≈C, A<C. When the tie falls through to configured order in the other direction the comparator is cyclic and `sort` output is implementation-defined. Latencies 20 / 65 / 110 ms, configured `wan, wireless, wired` → head is `wan`, axis `configured-order`; configured `wan, wired, wireless` → head is `wired`, axis `latency`. Same evidence, different typing order, and the WAN node wins while `selectionAxis()` tells the operator there was no evidence. Throughput behaves the same. Every registry test uses two endpoints.

Fix: evaluate the cascade as successive filters against the *best* value per axis (keep everything within threshold of the best on throughput, then of the best on latency, then capacity, then configured order). Thresholds against one reference form a total preorder, and `selectionAxis` becomes the last axis that eliminated anyone, true by construction. Add a three-endpoint test.

### H5 — Session minting has no timeout, and every request can inherit the hang
`src/api/SessionAuth.ts:21`, `:74`; `src/api/SessionManager.ts:171`, `:175`.

Both mint and validate call bare `fetch`. `SessionManager.fetch` awaits them on bootstrap and on 401 re-mint, and `fetchWithTimeout` cannot help because its controller is one the mint never observes. A black-holed first candidate (half-open TCP after a node dies) makes a cold start walk 2N untimed fetches, each waiting for the OS timeout, with every request in the app blocked on `inFlight`. `DEFAULT_REQUEST_TIMEOUT_MS`'s doc ("every request in the cluster status/catalogue/routing layer") is untrue for this path.

Fix: route both through `fetchWithTimeout(fetch, url, init, DEFAULT_REQUEST_TIMEOUT_MS)`.

### M3 — `PlaybackRuntime.retry()` rebuilds from the server echo
`src/playback/PlaybackRuntime.ts:301-325`.

### M4 — The carriage fix misses the standby path
`src/playback/ClusterPlaybackResolver.ts:126-134`, `:174-202` (unreleased).

`withServedSegmentContainer` runs only on the fresh-`create` branch of `failover`. `prepareAlternate` builds from raw preferences, and `failover` accepts a prepared alternate on endpoint id and `mediaId` alone: no mode check, no served-container check. The "fourth client" calling the resolver directly can promote an fMP4 standby onto an MPEG-TS failure, or a transcode standby onto a remux failure. The coordinator checks mode itself (`:1213-1217`, `:1548-1552`) but nothing anywhere compares served containers.

Fix: apply the helper in `prepareAlternate`; in `failover`, reject a prepared alternate whose mode differs or whose reported container differs. Tests for both.

**Severity revised down after evidence from the phone client (2026-09-12).** That client reports it has no coordinator at all: it calls `ClusterPlaybackResolver.failover` directly and never calls `prepareAlternate`. `prepareAlternate` has exactly one caller in the graph, the coordinator — so the standby half of this finding has **no live consumer today** and is a latent trap rather than a live defect. The `failover` half stands and is on that client's path, which is the part the unreleased diff's "every consumer passes rather than only the three that drive the coordinator" argument actually buys. The diff's rationale is right about `failover` and overstated about the standby path. Fix the standby gap when something starts preparing alternates without a coordinator, or fix it now cheaply to stop it becoming true silently.

### M5 — Failover double-charges the failed endpoint, and two teardown policies now coexist
`src/playback/ClusterPlaybackResolver.ts:170-172`, `:271-281` (unreleased); `src/playback/PlaybackCoordinator.ts:1447-1453`, `:1511-1533`, `:1581`.

`failover` records the failure once via `recordEndpointFailure` (cooldown 500 ms). The fire-and-forget `stop()` hits the same dead node, throws, and `stop` records again (2 s). Because `sessions.delete` only runs on success, the entry survives, so the coordinator's superseded cleanup DELETEs again → third record (10 s) → retries with backoff, each one another record. "Racing the coordinator's cleanup is harmless" is true of the HTTP side and false of the registry side.

Separately: the coordinator deliberately defers the old lease's DELETE until the replacement has buffered data, then retries with backoff. The resolver now DELETEs immediately, before the replacement is admitted. With a cluster resolver the deferral is dead code and `superseded-session-closed` logs a close that never happened. `ClusterNodeFailover.test.ts:74,88-93` still passes, but its single queued 204 is now consumed by the resolver's DELETE, so the test no longer exercises the deferral it describes.

Fix: `releaseFailedSession` should call `owned.resolver.stop` directly and drop the map entry regardless of outcome (the endpoint is already recorded and excluded). Then decide once which teardown policy is the paid-for one and delete the other; whichever survives, the integration test must assert it specifically (DELETE *before* first buffered event, or *only after*).

### M6 — The exclusion set never ages

### M7 — Watchdog blind spots on the platform it was written for
`src/playback/MediaWatchdog.ts:324-352`, `:326-332`, `:226-233`.

- After `suspend()`, `lastPositionMs` is kept and nothing re-arms: pause → node dies → resume = frozen forever. Only "paused is not stalled" is tested.
- `lastBufferedEndMs` is a running max, so after a backward seek buffer growth at the new position never counts as advancing and a healthy below-realtime transcode is evicted 7 s later — the eviction the class comment says it exists to avoid. **Raise this above the rest of M7 on evidence from the Android TV client (2026-09-12): on a TV the D-pad *is* the seek affordance**, and its `PlayerScreen.nudge()` commits a `runtime.seek` after every rewind burst. So this client emits backward seeks as ordinary viewing, not as an edge case, and condemns a healthy below-realtime node routinely. The observable is a failover roughly 7 s after any rewind. Web and phone have scrubbers people touch rarely, which is why it has stayed invisible.
- The +1 s margin comment says it only has to outlast the hold, but the watchdog reads only `currentTime`/`buffered`; a 500 carries no bytes, and hold + player retry delay + first byte exceeds 7 s. Either record the real relationship or state that holds do trip it and that is accepted.

### M8 — Background discovery records real routing evidence
`src/cluster/EndpointHealthMonitor.ts:230`; `src/services/createMachaServices.ts:67`; `src/cluster/endpointRouting.ts:144-166`.

`clusterStatusApi` routes through `route()`, so each 10 s discovery call does `recordSuccess`/`recordFailure`. ### ~~M9 — Cache-bust uses a clock that restarts at zero~~ — FIXED, unreleased (was: MEASURED, live bug)
`src/cluster/EndpointHealthMonitor.ts:57,61`; `src/runtime/host.ts:73-74`.

`cacheBustedProbeUrl` takes its value from `startedAt`, which is `machaHost().now()`, which is `performance.now()` in a browser and so restarts near zero on every page load. The comment's claim of "a URL nobody has seen before" does not hold.

**No longer hypothetical.** The web client measured it on the running client (2026-09-12): two consecutive reloads produced first-probe values of **744** and **571**, and a longer run gave 805, 18941 and 127451. Every value is a small integer, and the first probe of any load lands in a band a few hundred milliseconds wide because it fires at a fixed point in startup. So the value space for the first probe of a page load is a few hundred integers and is re-entered from the beginning on every reload. **Collisions are close to certain for anyone who reloads more than a handful of times**, and the failure is silent and in the worst direction: a cache anywhere on the path answers a probe for a node that is gone, and a dead node reports healthy.

Fix, keeping the reasoning already in that comment: reusing `startedAt` rather than taking a second clock reading is right, and the **latency** half must stay monotonic because it is a duration. Only the **cache-bust** half needs a never-repeating absolute value — take that from the wall clock, or from a counter seeded off it. That keeps both halves correct without reintroducing the second clock read the comment was avoiding. See the corrected L19: this is the same confusion as the persistence cases but running in the opposite direction, which is why it is worth naming alongside them.

### M10 — A storage write error kills the health loop silently

### M16 → **H6 — the connection gate cannot accept any endpoint against the live cluster. Measured.**
`src/connection/connectionConfiguration.ts:63-98`, `src/api/SessionAuth.ts:72-82`.

Originally written up as an inconsistency: `SessionAuth` treats a 401 from `/api/v1/catalogue/status` as "token rejected", so it believes that endpoint requires auth, while `checkEndpointConfiguration` hits the same route unauthenticated and counts an endpoint available only on `response.ok`. One of the two had to be wrong for every server.

**Upgraded 2026-09-12 on a measurement by the web client against Tom's live cluster: all three nodes answer 401 unauthenticated.** Confirmed in core's own logic — `:83-85` sets `receivedResponse` but returns `undefined` for a non-ok response, so `available` comes back empty and the result carries *"No configured endpoint accepted these connection details."* A caller that refuses to save on an empty `available` list therefore **cannot accept any endpoint a viewer types**.

That is a bootstrap lockout on a fresh install *for any caller that uses this function and refuses to save on an empty list*: no endpoint can be saved, so no session can ever be minted, so the client cannot be configured at all.

**Scope narrowed 2026-09-12.** The phone client checked and is **not** affected: its own `firstReachable` accepts a 401 as proof a node is listening, with a comment saying the probe runs before any session exists. So it independently reached the answer core's own doc comment states and core's code does not. The defect is in `checkEndpointConfiguration` and reaches whichever clients call it — measured on the web client — rather than being universal. That two implementations of one idea disagree, with the one *outside* core being right, is itself the finding: the rule belongs here and the correct version is currently in a client. The same path is the post-outage "check and reconnect". **It predates the users/roles work** (F2) rather than being caused by it, and it is invisible to anyone whose endpoints arrive from build configuration — which is why it has survived, since the reference client is configured from `.env` and never reaches the gate.

The doc comment at `:56-62` is the sharpest part: it says the check is "deliberately unauthenticated… It asks whether an address answers at all, which needs no credentials." **That reasoning is right and the implementation contradicts it**, because `response.ok` asks a stricter question than the comment poses. A 401 is an answer.

Two candidate fixes, and choosing between them is not core's call alone:

1. **Accept any HTTP answer as proof of life** — one line, matches the stated intent exactly. But it also accepts a 401 from something that is not Macha, which matters precisely when a viewer has mistyped an address.
2. **Point the check at a genuinely unauthenticated liveness route** — unambiguous, and lets the check confirm it is talking to Macha rather than to any server that refuses. Costs the server a route it does not currently expose.

Both are with the server session. Resolve this together with F2, which asks the same question from the other direction, and note that the tests here only exercise 200 and a `TypeError` — a 401 case would have caught it.

- **L19 (rewritten 2026-09-12 — the original was wrong and acting on it would have caused a silent bug).** Core has **two kinds of clock and they are not interchangeable.** `MachaHost.now()` is documented at `runtime/host.ts:23` as "milliseconds from an arbitrary origin, **for measuring durations only**", and `defaultNow` (`:72`) returns `performance.now()` wherever the host has it — monotonic, and reset to roughly zero on every run. `Date.now()` is the wall clock and the only one that can express an absolute instant.

  The original entry read as "three components default to their own clock rather than `machaHost().now()`" and invited a consistency sweep. **Two of those three must not be swept.** Sorted by what each actually needs:

  - **Durations, safe to route through `machaHost().now()`:** `ClientLog.ts:35,45` (`elapsedMs` is `now - startedAt`, entirely within one run) and `EndpointRegistry.ts:163` (`retryAt`/`lastFailureAt`/`lastSuccessAt` are only ever compared against the same clock in the same run). Switching these buys a host-supplied test clock and changes nothing else.
  - **Absolute instants, must stay on `Date.now()` — both are CORRECT TODAY and this entry is a "do not touch", not a defect.** `EndpointBandwidth.ts:55` takes `Date.now` as its constructor default and every caller uses that default, so the six-hour freshness window works as designed right now. It is listed only because a consistency sweep would break it: it persists `updatedAt` to storage and compares it after a restart against `this.now() - RESTORE_MAX_AGE_MS` (`:121-123`), so on a monotonic clock the post-restart `now()` is near zero, the cutoff goes hugely negative, and every persisted record would pass the freshness check regardless of real age — the window would silently stop existing. `MachaMediaApi.expiredCapability:47` is likewise correct today and compares against an expiry another machine signed, which a from-arbitrary-origin clock cannot express at all.

  The rule worth stating in `host.ts` itself: route a duration through the host clock, keep an absolute instant on the wall clock, and never convert between them. Related: `EndpointHealthMonitor`'s cache-bust (M9) is the same mistake already made in the other direction — it needs an absolute, never-repeating value and currently takes it from the monotonic clock.

## Added after the review — from the working tree, 2026-09-12

### ~~A1 — `expiredCapability` may compare seconds against milliseconds~~ — NOT A DEFECT, now pinned
`src/api/MachaMediaApi.ts:47-50` (uncommitted, added by the web client after this review was written). **Resolved 2026-09-12: `exp` is unix milliseconds, so the failure below does not occur.** Settled from the server source (`unix_ms()` is a `duration_cast<milliseconds>`, the TTL field is declared `std::chrono::milliseconds`, and verification compares the two directly with no conversion on either side) and from the wire (core's exact parse run over 41 live capability URLs: all thirteen digits, all classified live, expiring within the 24-hour default TTL). The gap was real even though the answer came out the other way — nothing pinned the unit, and a test now does: a capability an hour out in milliseconds re-hosts, the same instant in seconds does not, confirmed red against a seconds comparison. The digit-count normalisation suggested below was deliberately **not** added, on the stated reason that a format changing units should break loudly rather than be absorbed silently; the test is the thing that breaks. Kept here in full because the reasoning is the reusable part.

The function parses `exp` out of a signed artwork capability URL and compares it directly against `Date.now()`. That gates a new failover path: a live capability is re-hosted onto every node so a header-less image loader can fail over, and an expired one is re-hosted nowhere.

If the server signs `exp` in **seconds** — the usual convention, and what JWT specifies — the comparison is wrong by a factor of a thousand in the direction that hides itself. `Number(exp)` is about 1.76e9 against a `Date.now()` of about 1.76e12, so **every real capability reads as already expired**, `elsewhere` is always false, no re-hosted entry is ever produced, and `artworkUrls` returns exactly what it returned before the change. No crash, no failing test, no symptom: the feature is green in tests and absent in production. That is this package's own written rule about a fallback that never fires looking exactly like a fallback that is never needed.

The two new tests cannot catch it: both construct their own URLs (`?exp=${Date.now() + 60_000}`), so they assume milliseconds and pass by construction. Every pre-existing fixture uses `exp=1`, a placeholder rather than evidence. The live-cluster check reported alongside the change proves the *server* re-hosts, which is the premise, not that core's parse classifies a real capability as live.

**`expiredCapability` must keep reading `Date.now()` and must not be moved to the host clock** — see the corrected L19. It compares against an absolute instant chosen by another machine, which is exactly what a duration clock cannot express.

## Added after the accounts work landed — 2026-09-12

### A2 — Two clients now disagree about what logout means, and core documents no answer
`src/api/UsersApi.ts:128-135` (`logout`), `src/api/SessionManager.ts:148-166` (`signOut`).

The two operations are different and both are needed. `logout()` revokes the token server-side and the revocation propagates; `signOut()` drops it locally, clears the cache and mints a fresh anonymous session. Core's own comment on `logout` says plainly that dropping the token locally is not a logout.

The phone client calls `logout()` then `signOut()`, and reports a failed revoke rather than swallowing it — the viewer is signed out locally either way, and it says the old session stays live elsewhere until it expires. The web client calls `logout()` and never calls `signOut()`, so it holds a revoked token until some later 401 forces a re-mint, and every request in between carries a token the server has already revoked.

**One of these is wrong and core is why**: it ships two operations whose correct composition is written down nowhere. Do not merge the two behaviours or pick one by preference — compare the cases and state the answer on the API, which is the only place both clients read. The likely answer is that `logout()` should be the whole operation, or that the pair should be documented as an ordered idiom with the failure mode of each half.

### A3 — Playback must be stopped before sign-in and sign-out, and nothing says so
Raised by the phone client, which does it and notes core does not ask for it.

Changing identity does not close playback sessions — confirmed, nothing connects them — and **after the token changes, a playback session created under the old identity can no longer be closed**. The node then holds it against `max_video_transcodes` until `session_idle`, thirty minutes, on nodes configured with one slot.

So the ordering is an obligation on every caller, the fix is cheap, and the failure is invisible from the client that causes it. That combination is exactly what should not be left for three clients to rediscover separately. It belongs in the doc comments on `signIn` and `signOut` at minimum, and is the same slot arithmetic as the `terminateForPageExit` item already in ACTIVE.md.

## Forthcoming — the server's users/roles work

Not a review finding: a change coming from the server that the findings above will have to be re-read against. Recorded 2026-09-12 from the web client while the server design is still uncommitted, so nothing here is settled.

**F1 — a 401 stops meaning "expired", and `SessionManager` would sign a user out silently.** Changing a password or a role bumps a `credential_generation`, invalidating every session minted before it, cluster-wide and deliberately — a demotion that took up to thirty days to apply would not be a demotion. So a mid-session 401 becomes a normal event.

`SessionManager` answers a 401 by re-minting, and a re-mint with no credentials is an *anonymous* mint. An administrator whose roles change would therefore be silently downgraded to anonymous: sections vanish, writes start failing, and nothing anywhere says they were signed out. It fails quietly and disguises an auth event as a UI bug.

Shape of the fix when scoped: the session must remember whether it was authenticated. Anonymous 401 keeps re-minting invisibly as now; an authenticated 401 must stop, surface that the session ended, and let the application choose between re-login and a deliberate, visible drop to anonymous. The cached-session validation path on reload needs the same distinction.

This lands on top of **M12**, which already lists three state gaps in the same object — the dead token handed out during a reactive re-mint, the restart that adopts the old registry's result, and refusals misreported as unreachable. Whoever takes M12 should take F1 with it; fixing the mint paths twice would be worse than fixing them once.

**F2 — the probe endpoint becomes role-gated, which decides M16.** Both `validateAnonymousSession` (`SessionAuth.ts:72`) and `EndpointHealthMonitor` probe `/api/v1/catalogue/status`, which under the new model needs `media_viewer`. A user without that role would have every cached token classified dead on reload, and every node left permanently ungraded by the health loop — which silently takes out latency sampling and the preemptive swap along with it.

**M16 above is exactly this question** asked before there was an answer: it flags that `SessionAuth` and `connectionConfiguration` assume opposite things about whether that endpoint requires auth. The roles work settles it and makes the stakes concrete. The ask now with the server is one authenticated endpoint that needs no role (their `whoami` is the suggestion); if they agree, this is two call-site changes rather than anything structural, and M16 resolves with it.
